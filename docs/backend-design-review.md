# SideNote 后端设计方案 · 自评与风险清单

> 对 [backend-design.md](./backend-design.md) 的批判性自评。按影响分级：
> 🔴 **高** —— 会导致数据丢失 / 数据损坏，必须修；🟠 **中** —— 边界场景出错，应修；🟡 **低** —— 体验 / 性能 / 可维护性，建议修。
> 每条都给出触发场景与修复建议，最后附上线前验证清单。

---

## A. 数据一致性与竞态（本方案最大风险区）

### A1. 🔴 索引"读-改-写"竞态（read-modify-write race）— 核心缺陷

**问题**：`notes:index` 是单个数组 key，`updateNote` 的流程是"读整个 index → 改一条 → 写回整个 index"。当两个写入交错时（sidepanel 自动保存 + content script 剪藏，或同一上下文内"防抖 flush"与下一次 update 交错），后写者基于**过期快照**重写数组，会把先写者刚加入/更新的条目**整个覆盖掉**。

**后果**：`note:{id}` 正文还在磁盘上，但索引条目丢了 → 列表里"消失"的笔记（幽灵数据反向版）。`chrome.storage` 没有事务，这个洞是架构级的。

**修复**（任选，推荐第三条）：
1. **单写者队列**：所有索引变更串行通过同一个内存 Promise 队列（mutex），避免交错；
2. 写前重新读取最新 index（仍无法完全消除交错，不推荐单独用）；
3. **从根上消除整体重写**：索引改为 per-note key（`note:idx:{id}`，与正文同写同删），列表/搜索读时按需聚合或维护一个只读缓存。代价小、彻底解决 A1 与 B2。

### A2. 🔴 删除与防抖保存竞态（笔记复活 / 孤儿数据）

**问题**：编辑中（防抖 800ms 未落盘）→ 用户删除该笔记 → `deleteNote` 删掉 `note:{id}` 和索引条目 → 防抖缓冲随后 flush，把旧内容**写回磁盘**。结果要么整条笔记复活，要么磁盘上留下不在索引里的孤儿 `note:{id}`（占配额、搜不到）。

**修复**：
- `storage.ts` 增加 `cancel(key)` / `flushNow()`，`deleteNote` 先取消该笔记挂起的防抖写入；
- 写入带版本守卫：`updateNote` 携带期望的 `updatedAt`，写入前比对，过期写入直接丢弃；
- 同源风险：笔记在另一上下文被删时，编辑器内存中的内容会在下次保存时"复活"它 —— 保存前 `getNote` 校验存在性。

### A3. 🟠 双上下文并发初始化

**问题**：两个上下文同时发现 `meta` 缺失 → 各自写入默认库 → 重复默认文件夹 / 半初始化状态。

**修复**：初始化收敛到单点（background 或 sidepanel 应用启动时只执行一次）；默认文件夹用**固定 id**（如 `'inbox'`）并写入前复查，使重复执行幂等。

### A4. 🟠 迁移非幂等 + 并发迁移

**问题**：§5.6 提到 schemaVersion 迁移，但若迁移函数非幂等、且两个上下文同时迁移，可能双重执行损坏数据（`chrome.storage` 无 compare-and-swap 可用）。

**修复**：迁移函数必须幂等（重复执行结果相同）；迁移前后写校验和；约定"读时发现版本旧 → 迁移 → 写回新版本"，并把迁移本身做成可重入。

## B. 存储层细节

### B1. 🟠 两个"已证实"数值需要按目标 Chrome 版本复核

- 写入限流：超限确实抛 `MAX_WRITE_OPERATIONS_PER_MINUTE` 错误（[参考](https://stackoverflow.com/questions/66092333/chrome-extension-max-write-operations-per-minute-error?rq=1)），但**具体阈值与是否适用 storage.local** 各版本不同（storage.sync 明确 120 次/分钟；local 行为需实测）。文档应区分"已证实 / 待验证"，避免实现者采信错误数值。防抖 + 合并的方向不受影响。
- **多 key `setItems` 是否原子**：`chrome.storage` 文档未明确保证跨 key 原子性。必须写测试验证 `note:{id}` 与 `notes:index` 不会出现半更新（一条成功一条失败）。若不可靠，退化为"正文先写、索引后写 + 读时校验重建"。

### B2. 🟠 索引整体重写随笔记数线性放大

每写一条笔记都序列化整个 index（N 条 × ~100B）。2000 条时每次 autosave 序列化 ~200KB，虽不超配额但放大写入成本、加剧 B1 的限流压力。与 A1 同源，per-note 索引 key 一并解决。

### B3. 🟡 删除默认文件夹 / 当前选中文件夹

- 若目标是 `settings.defaultFolderId`（'inbox'），`moveNotesTo: 'inbox'` 指向**不存在的文件夹**；
- 前端 `selectedFolderId` 残留失效 id，且 `frontend-api.md` §7 里 `DEFAULT_NOTE_ID` / `DEFAULT_SEARCH_NOTE_ID` 这类硬编码复位逻辑在真实数据下失效（真实场景应"取列表最新一条"，而不是固定 id）。

**修复**：禁止删除默认文件夹（或删除后重选默认并同步 settings）；前端选择复位逻辑改为数据驱动。

### B4. 🟡 `pagehide` 异步 flush 可能被中断

侧边栏文档销毁时，挂起的异步 `chrome.storage` 写入可能未完成 → 丢失最后几键。**必须实测**：连打一段字后立刻关面板，重开验证。若不稳，用 `visibilitychange` 提前 flush + 更短防抖，或把写收敛到 background（方案 B 的核心动机之一）。

### B5. 🟡 `onChanged` 处理不当会写-触发-写死循环

标准做法：**onChanged 只刷新 UI，绝不回写**。文档需把这条写成硬性约定。

## C. 搜索

### C1. 🟠 混合结果排序与去重未定义

索引命中（title/excerpt）+ 全文扫描命中是**两路结果**，需要合并去重、按 `updatedAt` 统一排序，否则列表出现重复或乱序。文档应明确归并算法。

### C2. 🟠 静默不完整 + 结果计数误导

全文扫描限 200 条，超出部分的笔记即使命中也会被漏掉，但 UI 仍显示 `{{ count }} results in all folders`（frontend-api §5.7），用户会误以为搜全了。要么去掉"in all folders"措辞，要么明确标注"仅搜索最近 N 条"。

### C3. 🟠 扫描的 IO 成本

最多 200 条全文逐条 `get`（若逐个调用是 200 次往返）。**必须**用一次 `get(keys[])` 批量读取；且每键击（200ms 防抖）都做全文扫描，需要实测性能，必要时把全文索引升级为独立倒排 key（§7 已提）。

### C4. 🟡 编辑中的内容搜不到（索引滞后）

自动保存未落盘时，刚输入的内容不在 index 里 → 搜索不到。可接受，但应记录为已知限制；或搜索时对内存中未落盘缓冲做补充匹配。

### C5. 🟡 中文输入法组合态

composition 期间的 `input` 事件会触发多余搜索。前端需在 `compositionend` 后才发起搜索（项目作者是中文用户，这个不能省）。

## D. 消息协议（方案 B 备用）

### D1. 🟠 响应乱序（方案 A 同样存在）

`searchNotes` 全文扫描较慢，用户快速输入时，后发的查询可能先返回 → **旧结果覆盖新结果**。前端必须带请求序号，丢弃过期响应。方案 A 的直接 Promise 调用同样有该异步竞态，都要处理。

### D2. 🟡 自动保存不要走消息通道

MV3 service worker 休眠唤醒有延迟（首消息百毫秒级），自动保存经消息会放大 B4 的丢字风险。防抖 flush 应在 sidepanel 内直接写 storage。

### D3. 🟡 协议类型守卫

`ServiceRequest` 判别联合需要手写运行时守卫，易漏。建议配单元测试，或用 zod 之类校验（如后续引入）。

## E. 数据安全与内容

### E1. 🟠 剪藏/导入的外部 HTML 未消毒（XSS）

§7 计划支持剪藏，但 **Tiptap `setContent` 默认不做 XSS 消毒**，`markdownToHtml` 同样。剪藏/粘贴的外部 HTML 若含事件属性、危险 URL（`javascript:` 链接、`data:` 图片），在 `openOnClick`（未来）或图片预览等渲染路径构成风险。

**修复**：服务层在写入前做白名单消毒（DOMPurify）；`LinkPopover` 与 `setLink` 校验 URL scheme（仅 http/https/mailto）；当前 `autolink` 只认 http(s)，安全。

### E2. 🟡 明文存储

`chrome.storage` 明文，文档已注明；若未来剪藏全文/敏感内容，需 Web Crypto 加密（密钥放扩展内，权衡可恢复性）。

### E3. 🟡 卸载即全丢

没有导出/备份路径前，用户卸载或清除扩展数据即丢失全部笔记。建议早期加入导出（`markdownService` 已备），成本低。

## F. 其他边界

| # | 风险 | 说明与修复 |
|---|---|---|
| F1 | 🟡 时间戳排序不稳定 | `Date.now()` 同毫秒并列或用户改系统时钟 → 列表顺序抖动；加单调计数器或按 id 兜底 |
| F2 | 🟡 excerpt 生成缺陷 | 纯任务列表/代码块笔记可能 excerpt 为空；strip 标签后未解码 HTML 实体（`&amp;` 等）会显示乱码；空 excerpt 给占位文案 |
| F3 | 🟡 会话级 undo/redo 不持久化 | Tiptap 历史是内存态，自动保存后重开无法撤销到上次会话前 —— 明确为预期行为，避免用户误以为丢数据 |
| F4 | 🟡 `Folder.count` 每渲染 O(N) 计算 | 量级小可接受；量大时缓存计数，但引入一致性负担，谨慎 |
| F5 | 🟡 无请求取消/去重 | 快速点击新建/切文件夹会产生冗余调用；服务层加 in-flight 去重（同参同结果复用） |

## G. 上线前验证清单

- [ ] **并发写测试**：两上下文同时 `updateNote` / `deleteNote` / `createNote`，验证索引无条目丢失、无复活笔记（A1/A2）
- [ ] **删除 vs 防抖 flush 竞态**：输入后 800ms 内删除，确认磁盘无孤儿 key（A2）
- [ ] **关面板丢字测试**：连续输入后立即关闭侧边栏，重开验证最后内容完整（B4）
- [ ] **多 key setItems 原子性**：构造写失败场景，确认 `note:{id}` 与索引不会半更新（B1）
- [ ] **限流实测**：目标 Chrome 版本下连续写入，确认阈值与报错行为（B1）
- [ ] **搜索**：中文、大小写、空 query、正文命中、重复命中、limit 边界（C1/C2/C5）
- [ ] **迁移幂等**：v1→v2 重复执行、双上下文并发迁移（A4）
- [ ] **初始化幂等**：清空 storage 后双上下文同时首启（A3）

## 结论

方案**整体方向正确**：索引/正文分离、单条独立 key、防抖合并写入、unlimitedStorage、服务层无状态 —— 这些应对了配额与限流两大硬约束。

**必须优先修**：
1. A1 索引读-改-写竞态 + B2 索引整体重写 → 改用 per-note 索引 key + 按需聚合，一次解决两个问题；
2. A2 删除 vs 防抖保存竞态 → 取消机制 + 版本守卫；
3. C1/C2 搜索语义 → 定义归并排序，修正结果计数文案。

**次要必做**：E1 内容消毒（剪藏前）、B4 关面板丢字实测、D1 响应乱序守卫、B3 默认文件夹保护。

其中 A1/A2 属于"修完必须写并发测试"的级别 —— 这两处是当前设计里唯一可能造成用户数据静默丢失的缺陷。
